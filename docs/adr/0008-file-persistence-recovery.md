# ADR-0008：文件为计算单位，快照持久化与崩溃恢复

- 状态：已接受（模型与需求；自动保存参数/存储位置等待确认）
- 日期：2026-11-21
- 关联：[ADR-0007](0007-backend-layering.md) · [后端设计 §6](../architecture/backend.md#6-持久化与崩溃恢复)

## 背景

产品要求：

1. 实时计算“像一整个 Excel 文档一样，只在一个文件内更新”；
2. 数据快照需要快速持久化；
3. 系统崩溃后能够恢复。

若引入跨文件计算图或数据库事务体系，会显著增加复杂度；而桌面单机场景下，文件就是天然的一致性边界。

## 决策

### 1. 文件是计算、持久化与隔离的基本单位

- 一个打开的文件拥有自己的 `FileRuntime`：文档状态、Dataset 缓存、刷新调度、插件函数调用上下文；
- 更新只在文件内传播；文件之间没有隐式联动；
- 文件级错误边界：数据源/插件失败只影响该文件对应部分。

### 2. 三类快照

| 类型       | 内容                                                | 触发                    |
| ---------- | --------------------------------------------------- | ----------------------- |
| 文档快照   | FileDocument（workbook + 数据源 + 视图 + revision） | 显式保存 / 自动保存     |
| 数据快照   | 解析后的 Dataset（版本、校验和、来源元数据）        | 手动刷新成功 / 首次导入 |
| 恢复检查点 | 文档快照 + 数据快照引用 + 元数据                    | 自动保存                |

### 3. 原子持久化

写临时文件 → `fsync` → `rename` 覆盖，保留 `.bak`；快照携带 `schemaVersion`、`coreApiVersion`、`fileId`、`revision`、`savedAt`、`checksum`。校验失败按「最新检查点 → `.bak` → 最后显式保存」回退。

### 4. 自动保存与恢复

- 仅 dirty 时保存；防抖 1–2s、最长间隔 10s；切换文件/退出时立即落盘；
- 写盘在阻塞线程执行，不阻塞请求处理；空闲时无后台 IO/定时器；
- 启动时通过会话标记检测非正常退出，校验后提示恢复；恢复内容为文档 + 数据快照，不含瞬时 UI 状态；
- 刷新失败保留上一次成功的数据快照，不覆盖。

### 5. v1 不引入 SQLite

文件 + 原子写足以满足单机、单写者场景；SQLite（WAL）作为“测量后如果确有需要”的演进选项，而不是默认方案。

## 理由

- 文件边界让持久化、恢复、隔离三者共用同一模型，实现简单且语义清晰；
- 全量快照 + 原子替换避免了增量日志重放不一致的风险；
- 手动刷新 + 数据快照缓存解决了“源文件丢失/变化”下的可恢复性，同时不引入后台监控。

## 后果

- 优点：崩溃恢复可靠、实现简单、无数据库运维；文件之间天然隔离。
- 成本/风险：
  - 自动保存是全量序列化，超大文档需要测量；若不足，再引入增量日志/SQLite；
  - 快照文件体积可能较大，需要上限与清理策略；
  - 手动刷新意味着数据可能过期，产品上必须明确展示“数据快照时间”。
- 恢复丢失窗口默认约 10s（可调，见待确认项）。

## 备选方案

- **每次修改提交 SQLite 事务**：实现与依赖更重，且没有解决 Univer 快照序列化成本；后置。
- **增量 mutation 日志 + 定期 checkpoint**：恢复更快、写盘更小，但需要可靠的日志重放与压缩；v1 不做。
- **仅显式保存、无自动保存**：崩溃损失大，不满足需求。
