# ADR-0005：计算引擎分层——本地交互引擎 + Rust 权威/扩展引擎

- 状态：已接受（分阶段实施）
- 日期：2026-11-21

## 背景

若所有计算都放 Rust：

- 每次输入公式都要网络往返，失去 Excel 式的即时感与离线能力；
- 但若所有计算都放前端，自定义函数（可能访问本地数据、需要权限、体积大）无法安全/方便地实现，AI 工具也无法获得可信的“服务端真值”。

这是一个典型的**延迟 vs 能力**权衡。

## 决策

采用分层策略：

1. **交互引擎（现在）**：Univer 的 TypeScript 公式引擎，负责所有内置公式、格式与即时重算。离线可用、零延迟。
2. **扩展引擎（v0.2）**：Rust 侧提供自定义函数注册表 + WASM 沙箱（`wasmtime`），以及 AI 工具执行。前端通过受控 RPC 调用（Univer 自定义函数/RPC 机制），结果异步回写单元格。
3. **权威/批处理引擎（按需）**：当需要服务端统一计算（导出 xlsx、批量重算、插件市场校验）时，评估 [`formualizer`](https://crates.io/crates/formualizer) 作为 Rust 公式引擎，或用自有 AST 求值器；其职责是“权威结果”，而不是替换交互引擎。

同时建立**口径一致性约束**：

- 定义一份“公式一致性测试向量”（输入表 + 公式 + 期望值），前端引擎与 Rust 引擎都跑同一份；不一致时以 Excel 行为为仲裁。
- 自定义函数在 manifest 中声明 `deterministic`、`volatile`、`async`、权限；非 deterministic 函数明确不可用于导出快照的缓存结果。
- 快照中保存的是公式文本而非缓存值；缓存值仅用于渲染，避免两份数据源冲突。

## 后果

- 优点：保留即时交互与离线；扩展能力不被前端限制；Rust 侧可做权限与审计。
- 成本/风险：
  - 两种引擎可能出现结果差异；用测试向量 + 明确的“交互/权威”边界来管理。
  - 异步自定义函数需要处理单元格“计算中”状态、超时、错误传播与撤销。
  - WASM 插件需要沙箱、资源限额、宿主函数白名单。
- 明确不做：现在不实现完整 Rust 公式引擎，也不要求两侧 100% 一致。

## 备选方案

- **全部前端**：扩展函数需下载 JS/WASM 到浏览器，权限与本地数据访问弱，AI 也无法用服务端可信结果；不采用。
- **全部 Rust（前端只做渲染）**：延迟与离线体验不可接受；不采用。
- **仅用 formualizer 替代 Univer 引擎**：Univer 的编辑体验依赖其引擎集成，替换成本高；作为“权威引擎”评估更合理。
